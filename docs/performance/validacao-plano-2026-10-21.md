## Execução recomendada, com gates

1. **P0 — congelar baseline sem tocar na worktree original.** Registrar HEAD, branch e estado dirty. Criar snapshot temporário por allowlist que inclua o código local rastreado alterado e auxiliares não rastreados necessários (incluindo `src/features/comercial-v3/import-file.ts`); produzir manifest privado com os paths e hashes dos arquivos de código copiados, sem segredos, fixtures reais ou conteúdo comercial. Não usar somente o commit remoto como baseline. Excluir `.git`, `.env*`, `.claude/`, `.agents/`, `legado/`, `node_modules`, `.next`, `out`, `dist`, caches, `.scratch`, evidências, fixtures/dados reais e backup `.tmp`. Não confiar só no `.gitignore`. Reaproveitar dependências somente se resolução de módulos não escapar nem carregar configuração/env do repo original; caso contrário, parar, sem instalar dependências nesta etapa. Confirmar Tailwind scan paths, webpack root e contexto do Next na cópia.
2. **P0 — saída de build e servidor.** Na cópia descartável apenas, executar o build estático correspondente (`npm run build:static`, não o agregador que apaga `dist`) com `NEXT_PUBLIC_IMPORT_STORAGE` explícito e registrado; confirmar `out/` novo. Servir `out` em origem/porta fixa, sem `next dev`, e manter essa origem entre corridas porque IndexedDB é por origem. Build compartilhado exige as rotas Worker `/api/imports/*`; sem backend local autorizado, limitar conclusão a shell/carga inicial e marcar o fluxo compartilhado como **NÃO VERIFICADO** — não chamar o modo IndexedDB de produção. Se isolamento, ambiente, dependências, outputs ou raízes de resolução não puderem ser assegurados, parar. Build local não valida D1 nem produção.
3. **P1 — baseline inicial de baixa intrusão.** Desktop 1440×900 primeiro, URL/view e dados sintéticos reproduzíveis. Fixar e registrar a origem; manter a mesma origem entre corridas para preservar estado IndexedDB, ou resetá-lo deliberadamente como cenário separado. Registrar cache frio/quente separadamente. Iniciar com 100 linhas e cinco amostras por cenário; relatar mediana e faixa min–max, não P75, P95 nem significância. Usar coleta mínima/baixa sobrecarga, anotar instrumentos e manter a mesma configuração em comparações. LCP/CLS são métricas de carga; INP requer interação representativa e medição de latência/event timing/identificação de interação. Cinco execuções de laboratório não produzem INP de campo nem percentil Core Web Vitals.
4. **P1-D — diagnóstico separado.** Coverage (após exercitar interações), heap snapshots, GC forçado, pintura avançada e React Profiler são coletas diagnósticas separadas, não misturadas à linha de base. Trace leve de Performance pode ser usado se necessário; registre a instrumentação e compare antes/depois com a mesma opção. Profiler React em dev localiza re-render, não se compara quantitativamente com produção; build de profiling difere do padrão e tem overhead. Coverage não prova código inútil sem interações cobertas. Heap JavaScript não é memória GPU; headless/Windows GPU fallback e FPS não garantem hardware real. Viewport/CPU throttle mobile não substituem aparelho físico.
5. **P2 — decomposição de custos, sem otimizar.** Isolar JS inicial/chunks reais, renders e cálculos React, trajetória SVG/ResizeObserver/ponteiro/teclado, Motion e CSS (aurora, filtros, blur/backdrop). Distinguir CPU principal, pintura, composição e memória gráfica; identificar evidência antes de sugerir qualquer alteração.
6. **P3 — importação, memória e persistência.** Expandir adaptativamente, sem matriz cartesiana: testar viewport 375×812/reduced-motion e 5k–10k/50k somente se a hipótese justificar, com fixtures sintéticas e limites seguros; XLSX/CSV até 15 MB são limites de aceitação, não obrigação de executar já. Medir separadamente leitura, SHA-256, parse CSV/XLSX no Worker, transferência/clone, normalização/reconciliação/modelos, prévia/render, gravação IndexedDB/reload, snapshots/histórico. Worker de parsing não prova que as demais etapas deixem a UI livre. Exercitar histórico 1/3/4/20 apenas no regime aplicável. D1/API compartilhada é cenário separado, sem runtime privado, migração, mutação de banco ou deploy.
7. **P4 — priorizar.** Para cada gargalo comprovado, registrar cenário reproduzível, evidência/componente, impacto observado, esforço/risco, hipótese de melhoria, métrica comparável e regressões possíveis. Não antecipar virtualização, cache, lazy loading ou remoção de Motion/blur sem evidência.
8. **P5 — otimização condicionada.** Ainda não autorizada. Somente após autorização específica, uma hipótese por alteração, menor diff reversível, revisão adversarial, testes funcionais/técnicos e reteste pareado no mesmo ambiente. Aceitar apenas se benefício observado superar regressões/custos.
